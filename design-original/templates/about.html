Architecture de VoyaGo

Projet du Groupe 15 · Architecture logicielle et objets répartis · ENSP Douala

Monolithe modulaire

L'application est découpée en 6 modules indépendants (auth, trip, booking, payment, notification, backoffice), chacun organisé en couches api / web → application → domain ← infrastructure (architecture hexagonale).

Les modules ne lisent jamais les tables des autres : ils communiquent par des services publics, des ports (ex. SeatOccupancyPort) et des événements métier. Chaque module peut donc devenir un microservice sans refonte (plan de repli prévu au cahier des charges, section 6.2).

Saga réservation ↔ paiement

  1. Réservation créée « en attente », sièges verrouillés 15 min.
  2. Paiement initié auprès de l'opérateur (Strategy / Adapter).
  3. Webhook signé → événement PaymentConfirmed.
  4. Booking confirme et émet les billets → BookingConfirmed.
  5. Notification envoie l'e-mail avec le PDF (après validation de la transaction).
  6. Compensations : expiration → paiements annulés ; annulation → remboursement ; paiement tardif → remboursement intégral.

Aucune double vente (RG1)

Chaque siège occupé est une ligne de la table seat_reservation avec une contrainte d'unicité (voyage, siège) : si deux clients valident au même instant, la base refuse le second. Les verrous expirés sont libérés par une tâche planifiée. S'y ajoutent le verrouillage optimiste (@Version) et l'idempotence des paiements.

Patrons de conception

  • Repository : Spring Data JPA
  • DTO : records de l'API REST
  • Strategy / Adapter : PaymentProvider (MTN MoMo, Orange Money, espèces)
  • Factory : NotificationFactory (e-mail, SMS)
  • Observer : événements de domaine
  • State : BookingStatus et ses transitions
  • Saga : réservation ↔ paiement avec compensations
